## 2. ①②④ 앙상블 스프레드 0 — 원인과 해결

### 원인
`_overwrite_forecast_rows()` 는 base 기상파일에서 **예측기간에 해당하는 행만** 멤버 값으로
덮어쓴다. 관측이 2024 까지인데 2026 을 예측하면 그 행 자체가 없어 주입이 일어나지 않고,
SWAT+ 가 전 멤버에 **동일한 기상발생기(wgn) 날씨**를 쓴다. 오류도 나지 않고 종료코드 0 이다.

실측 근거 (쿡, 수정 전):

| 관측소 | 예측기간(2/1~4/30) 89일 중 보유 |
|---|---|
| `427608.pcp` | 34일 |
| `461412.pcp` | 28일 |
| `461303.pcp` | **0일** |
| `918430.pcp` | **0일** |

2026 자료가 일부 있던 관측소를 쓰는 유역(avana)만 멤버별로 값이 달랐고(451/954),
0일인 유역(avatiu·takuvaine·ngatoe)은 **954멤버 전부 같은 값**이었다.

### 왜 지금까지 드러나지 않았나
기존 실행은 `2016_AMJ` — **관측 기록 안의 과거 기간**이라 덮어쓸 행이 존재했다.
이번이 관측 밖의 실제 미래 예측 첫 실행이라 결함이 드러났다.

### 해결 (`swat_py/drought/dashboard_data.py`)
결정: **ERA5 실측 연결을 우선하고, 불가할 때만 wgn 연장**한다.

1. `fill_base_weather()` — ①관측소별 최근접 ERA5 격자 일자료로 warm-up~예측 끝월 재구성
   → ②실패 시 결측(-99) 행으로 연장(SWAT+ wgn 보완)
2. `extend_weather_to()` — `.pcp`/`.tmp` 연장 + **`nbyr` 헤더 갱신**
3. `_assert_forecast_weather_rows()` — 확보 실패 시 **실행 전 중단**
4. `resolve_era5_inputs()` — 격자점 CSV 가 `era5/` 또는 `gis/era5/` 어디에 있어도 인식

### 검증
`[base] 기상 = ERA5 실측 연결 (격자 매칭 7개소, 실측 최신 2026-04-29)` —
예측기간 89일 **전부 실측**으로 확보. 앞서 ERA5 를 2026-07 까지 갱신해 둔 덕분이다.

## 3. 멤버 실패율 12.6% — 관측 결측의 전파

### 원인 사슬
```
관측 강수 결측(쿡 918430: NaN 214일)
  → numpy 월합계가 NaN
  → NaN 은 두 경계 비교가 모두 False → else 분기(AN)로 낙하 → AN pool 오염
  → 그 값을 뽑은 멤버: target=NaN → scale=NaN → 그 달 강수 전체 NaN
  → SWAT+ 멤버 실패
```
2·3·4월 126개월 중 **13개월(10.3%)** 에 결측일 존재 → 1000멤버 중 **126개(12.6%)** NaN.
NaN 패턴도 정확히 일치했다(prcp 컬럼만, 멤버당 28·30·31일 = 한 달 통째).

2026 FMA 예측이 강수 AN 우세여서 오염된 AN pool 을 뽑는 멤버가 많았던 점이 결정적이다.

### 해결 (`acidwg_py`)
- `_build_obs_monthly_pool()` — 결측월을 pool 에서 제외(강수·기온 모두)
- 경계 산정(`run.py`, `modeling/precipitation.py`) — `np.quantile` 에 **유한값만** 사용.
  결측월이 있으면 경계가 NaN 이 되어 **그 달 전 연도가 AN 으로 오분류**되던 문제도 함께 해소
- 보정 단계에 target 유한성 2차 방어

### 검증
acidwg 재생성 후 **쿡·팔라우 각 1000멤버 중 NaN 0개**(이전 126개).

## 4. ③ 저수지 historical mean — 원인과 해결

### 원인
대시보드 저수지 분기가 `series["hist_mean"] = float("nan")` 로 **의도적으로 NaN** 을 넣고
있었다. 하천은 climatology CSV 에서 월평년을 가져오지만, 저수지는 저수량% 기준이라
대응하는 평년이 climatology 산출물에 없었기 때문이다.

### 해결 — 예측과 **동일 소스**로 평년 산출
채널유량을 유입으로 쓰지 않은 것이 핵심이다. Ngerimel 은 용량(0.10 MCM)이
채널 월유량(0.87 MCM)보다 훨씬 작아, 채널유량으로 계산하면 매월 만수로 재충전되어
예측(저수지 `flo_in` 기반)과 기준이 어긋난다.

- `climatology_run.py` — 저수지 수원이 있으면 `print.prt` 의 reservoir 일단위 출력을 켜고,
  `write_reservoir_climatology()` 가 `reservoir_day.txt` 물수지를 연도별로 돌려 월 평년 산출
  → `reservoir_monthly_avg_{tag}.csv`
- `dashboard_data.py` — `reservoir_climatology_monthly()` 로 읽어 `hist_mean` 매핑
  (파일 없으면 NaN, 구 climatology 하위호환)

### 검증 (팔라우 ngerimel, 만수대비 %)

| 월 | hist_mean | forecast_mean | p5 ~ p95 |
|---|---|---|---|
| 2 | 326.2 | 451.9 | 8.7 ~ 1207.6 |
| 3 | 273.3 | 293.4 | 48.0 ~ 587.6 |
| 4 | 326.3 | 332.3 | 23.1 ~ 731.5 |

`hist_mean` NaN 0/12. 평년과 예측이 같은 척도에서 비교된다.

## 5. ⑤ 저수지 과속 고갈 — 두 겹의 원인

### (a) 앙상블 미주입 (해결)
전 멤버가 동일한 wgn 날씨를 쓰면서 3·4월이 일제히 0 이 되었다. 수정 후 해소.

### (b) 구조적 제약 (미해결, 설계 판단 필요)
Ngerimel 댐 실측 수치:

| 항목 | 값 |
|---|---|
| 만수(여수로 45 ft) 저수량 | **103,242 m³** |
| 사수위(23.34 ft) 저수량 | **0 m³** |
| 상수도 취수 0.0438 m³/s | 월 **113,530 m³** |

**월 취수량이 총 저수량보다 크다.** 유입이 없으면 **27일 만에 완전 고갈**된다.
월 단위 물수지로는 0% 아니면 수백 % 의 양극단만 나올 수밖에 없는 구조다.
"Crisis 는 어쩌다 한 번 나와야 한다"는 지적을 충족하려면 다음 중 하나가 필요하다.

1. 일 단위 물수지로 전환(월 해상도의 한계 제거)
2. 취수량 재검토(현재 1 MGD 문헌값) 또는 월별 실측 반영
3. 예측 초기조건(`initial_condition.init_water_level_ft`) 현실화

`dead_m3 = 0` 도 확인이 필요하다 — 사수위에서 저수량이 0 이면 하한 보호가 작동하지 않는다.

## 6. `storage_pct` 1315% — 버그 아님

```python
supply = 월초저류 + 순유입 − 취수
pct    = max(supply, dead_m3) / full_m3 * 100     # 상한 없음(월류 표시)
S      = clip(supply, dead_m3, full_m3)           # 이월 저류는 정상 clip
```
docstring 에 "월류 월은 >100 → Normal" 로 명시된 **의도된 설계**다.
다만 이 댐은 유입이 용량의 수 배라 평년조차 273~660% 로 나온다.
대시보드에 "만수대비 %"로 표시하기에는 부적절하며, ⑥ 해결 시 함께 정리해야 한다.

## 7. ⑥ 수위 출력 — 미해결 (다음 과제)

두 부분 모두 남아 있다.

**(a) 대시보드 주 지표가 저수량 %**
`series.csv`·`thresholds`·`stage_prob`·그래프가 모두 `storage_pct` 기준이다
(`thresholds.method: capacity_fraction`). `water_level_ft` 는
`3_swatplus/forecast/{period}/{outlet}.csv` 에만 기록된다.
설정 주석에도 "대시보드 저수량 입력 연계는 후속"으로 남아 있다.

**(b) 기준면(datum) 미적용**
기존 산출물의 `water_level_ft` 범위는 **23.34 ~ 45.00** — MSL 곡선 datum 그대로다.
이메일 지적("만수 45 → 실측 23, 22 차감")과 같은 상태다.
설정에는 이미 `obs_datum_offset_ft: -22.0` 이 있으나(45−22=23),
코드 검색 결과 `historical_worst.py` 에서만 쓰이고 **예측 경로에는 적용되지 않는다**.
`ReservoirForecastParams` 에 offset 필드 자체가 없다.
