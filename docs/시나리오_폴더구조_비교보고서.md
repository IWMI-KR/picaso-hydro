# 시나리오 폴더 구조 — 두 가지 안 비교 및 권장안

> PICASO-Hydro 의 *공식 확률예보 / 평년값 / 최악 가뭄 / 사용자 정의 시나리오* 를 지원하기 위한
> `acidwg_py` 출력 폴더 구조 두 가지 안의 장단점 비교와 권장안.
>
> 작성: IWMI-KR · 2026-05-12 · PICASO-Hydro 개발 산출물

---

## 1. 비교 대상 두 가지 안

### 안 A — Scenario 를 operational/hindcast 의 하위 컨테이너로 통합 (개발자 초기 제안)

```
1_acidwg/
├ operational/{year}/{season}/
│   ├ default/        member_0001..1000/<stn>.csv   ← 기존 공식 확률예보
│   ├ climatology/    member_0001/<stn>.csv         ← 평년값
│   └ worst_drought/  member_0001..N/<stn>.csv      ← 최악 가뭄
│
└ hindcast/{year}/{season}/
    └ default/        member_0001..1000/<stn>.csv
```

핵심 — **시나리오가 각 운영 모드(operational, hindcast)의 *하위 컨테이너* 로 들어감.** 모든 출력은 `{mode}/{year}/{season}/{container}/member_*` 의 4-level 컨벤션으로 통일됨. 기존 `member_*` 폴더는 `default/` 컨테이너 아래로 마이그레이션 필요.

### 안 B — Operational / Hindcast / Scenarios 3축 최상위 분리 (사용자 요청)

```
1_acidwg/
├ operational/{year}/{season}/member_0001..1000/<stn>.csv      ← 변경 없음
│
├ hindcast/{year}/{season}/member_0001..1000/<stn>.csv          ← 변경 없음
│
└ scenarios/{year}/{season}/                                     ★ NEW
    ├ climatology/        member_0001/<stn>.csv
    ├ worst_drought_2016/ member_0001..N/<stn>.csv
    └ <user_defined>/     member_*/<stn>.csv
```

핵심 — **시나리오를 operational / hindcast 와 동등한 최상위 분석 모드로 분리.** Scenarios 폴더는 *현재 시점의 예측 기간* 에 대해서만 생성되며, 평년값·최악 가뭄은 빌트인이고 사용자가 yaml 로 추가 시나리오를 정의할 수 있다. 기존 operational/, hindcast/ 폴더는 손대지 않는다.

## 2. 항목별 비교

| 비교 항목 | 안 A — 계층 통합 | 안 B — 3축 분리 |
|---|---|---|
| 개념적 분리 | scenario = operational/hindcast 의 *변형* | scenario = 독립적 *what-if 분석* 도구 |
| 폴더 깊이 | 4 단계 (mode/year/season/container) | operational/hindcast 3단계, scenarios 4단계 |
| 코드 분기 | mode + container 두 인자 | mode 단일 인자 (scenarios 만 container 추가) |
| hindcast 와 시나리오 결합 | 가능 (예: hindcast/2016/JJA/worst_drought) | 미지원 — 별도 처리 필요 (현재 요건 외) |
| "현재 시점 전용" 제약 표현 | 코드 검증으로 보장 (폴더 구조는 무관) | 폴더 자체가 의미 — 검증 코드 불필요 |
| 검색·네비게이션 | mode 4축, container 4축 → 16조합 | operational/hindcast 그대로, scenarios 만 진입 |
| 권한·정책 분리 | container 단위 권한 매핑 복잡 | scenarios 만 사용자 변형 허용 등 단순 |
| 백업·정리 | 시나리오와 공식 예보가 같은 트리에 혼재 | scenarios 통째로 백업/삭제 가능 |
| Dashboard 노출 | "operational 의 worst_drought" 라는 모순적 라벨 | "공식 예보 vs 시나리오" 토글 자연스러움 |
| 마이그레이션 비용 | 기존 모든 member_* 폴더를 default/ 아래로 이동 | 비용 0 — 기존 폴더 그대로 유지 |
| 일관성 | mode 모두 동일한 4-level 구조 | operational/hindcast 동일, scenarios 만 1축 추가 |
| 사용자 정의 시나리오 위치 | operational 안에 user_xx 혼재 | scenarios/user_xx/ 로 격리 |
| Dashboard 데이터 트리 | data/operational/{loc}/{model}/{container}/ | data/{operational,scenarios}/{loc}/{model}/ |
| swat_py 코드 변경량 | mode + container 두 인자 추가 | mode 인자 + scenarios 전용 분기 |
| 폴더 트리 가독성 | 시나리오가 operational 부산물처럼 보임 | 세 가지 목적이 한눈에 보임 |

## 3. 정성적 평가

### 안 A — 계층 통합

**장점**

- 모든 모드가 동일한 4-level 폴더 컨벤션을 공유 → 코드 추상화가 균일하다.
- hindcast 에 대해서도 시나리오 변형이 가능 (예: "2016년 hindcast 에 -30% 강수 시나리오").
- mode 와 container 가 단일 dispatcher 로 표현 가능.

**단점**

- 시나리오는 본질적으로 "공식 예측을 대체하는 *what-if* 분석" 인데, operational 의 변형으로 격하되면 **분석 의도가 흐려진다.**
- Dashboard 사용자에게 노출할 때 "Operational 의 worst_drought" 는 라벨이 모순적 — *공식인데 시나리오?*
- scenarios 가 hindcast 폴더 안에도 등장하면 의미가 불명 — *과거 시점의 가상 시나리오?* 라는 질문이 발생.
- 기존 member_* 폴더를 모두 default/ 아래로 옮기는 1회성 마이그레이션 필요 — 운영 중 자료가 있으면 비용 발생.
- 사용자 정의 시나리오가 공식 예보 폴더와 같은 트리에 섞여 들어가 권한·백업 정책 분리가 어렵다.

### 안 B — 3축 분리

**장점**

- "공식 예보 / 검증(hindcast) / what-if 분석(scenarios)" 의 세 가지 목적이 **폴더 구조로 자기설명적**.
- scenarios = "현재 시점 예측 기간 전용" 이라는 제약이 **폴더 자체로 강제**됨 — 별도 검증 로직 불필요.
- **마이그레이션 비용 0** — 기존 operational/, hindcast/ 폴더와 코드를 건드리지 않음.
- 사용자 정의 시나리오가 공식 예보 폴더를 오염시키지 않음 — 권한·백업 정책 분리 용이.
- Dashboard UX 가 자연스러움 — "공식 확률예보 보기" 와 "시나리오 비교 보기" 토글이 사용자의 mental model 과 일치.
- 운영자가 scenarios 폴더만 통째로 백업하거나 삭제할 수 있어 운영 정리가 단순.

**단점**

- hindcast 에 시나리오 변형을 적용하려면 별도 위치가 필요 — 그러나 현재 요건에 포함되지 않음.
- 안 A 대비 운영자가 *새로운 최상위 폴더 1개* 를 더 학습해야 함 — 학습 비용은 작음.
- 시나리오 폴더만 4-level (`scenarios/{year}/{season}/{name}`) 로 비대칭 — 코드에서 분기 1회 필요.

## 4. 코드 영향도 비교

| 변경 위치 | 안 A | 안 B |
|---|---|---|
| acidwg_py 출력 경로 | `run.py` 내부 1줄 수정 (member_path 에 container 추가) | `scenarios/` 신규 서브패키지 + CLI 1개 (`acidwg-scenarios`) |
| `EnvConfig` 속성 | `EnsembleDir` 그대로 + container 인자 | `OperationalDir` / `HindcastDir` / `ScenariosDir` 3개 분리 |
| `forecast/ensemble.py` | `mode`, `container` 2개 파라미터 | `mode`, `scenario_name` 2개 파라미터 (의미는 명확) |
| `dashboard/build.py` | `data/{mode}/{loc}/{model}/{container}/` 단일 트리 | `data/{operational,scenarios}/{loc}/{model}/` 분리 트리 |
| 마이그레이션 | 기존 operational/, hindcast/ 의 모든 member_* 폴더를 default/ 아래로 이동 | 없음 — scenarios/ 신설만 |
| 호환성 분기 (backwards-compat) | 필요 (default/ 없으면 부모 폴더 fallback) | 불필요 |
| 단위 테스트 작성량 | 모드×컨테이너 매트릭스로 증가 | 모드 단위로 분리되어 명확 |

**핵심: 안 B 의 마이그레이션 비용이 0** 인 반면, 안 A 는 운영 중 자료가 누적되어 있다면 1회성 폴더 재배치 작업이 필요.

## 5. 어떤 상황에서 어떤 안이 더 좋은가

| 상황 / 우선순위 | 더 적합한 안 |
|---|---|
| 운영 중 자료가 이미 누적되어 있다 | **안 B** (마이그레이션 비용 0) |
| hindcast 에 시나리오 변형 적용 요건이 미래에 확실히 있다 | 안 A |
| Dashboard 에서 "공식 vs what-if" 의 분리가 중요하다 | **안 B** |
| 사용자가 만든 시나리오 폴더의 격리·권한이 중요하다 | **안 B** |
| 한 가지 폴더 컨벤션으로 코드를 통일하고 싶다 | 안 A |
| scenarios 의 "현재 시점 전용" 제약을 강제하고 싶다 | **안 B** (구조로 강제) |
| 학습 곡선·문서화 비용을 최소화하고 싶다 | **안 B** (목적별 분리로 직관적) |

PICASO-Hydro 의 현재 요건은 **scenarios 의 *현재 시점 예측 기간 전용* 제약** 과 **사용자 정의 시나리오의 격리** 가 핵심이므로, 항목별 매핑이 안 B 쪽으로 크게 기울어진다.

## 6. 권장안 (Best Practice)

**권장 — 안 B (Operational / Hindcast / Scenarios 3축 분리).**

### 근거 (요약)

1. **의도가 폴더 구조로 자기설명적** — scenarios 가 별도 축으로 분리되어 "공식 / 검증 / what-if" 세 목적이 한눈에 보인다.
2. **마이그레이션 비용 0** — 기존 operational/, hindcast/ 폴더와 코드를 건드리지 않는다.
3. **"현재 시점 전용" 제약이 구조로 강제됨** — 코드 검증 로직 없이 폴더 위치 자체가 의미를 전달.
4. **Dashboard UX 가 자연스러움** — 공식 예보 vs 시나리오 비교의 분리가 사용자 mental model 과 일치.
5. **사용자 변형의 격리** — 사용자 정의 시나리오가 공식 폴더를 오염시키지 않으며, 권한·백업 정책 분리가 가능.

### 권장 추가 사항

- **operational/, hindcast/ 폴더 모양은 변경하지 않는다** — `default/` 컨테이너 도입은 *하지 않음*. 마이그레이션 비용을 피하고, 안 B 의 본래 의도(기존 모드 보호)를 유지한다.
- **swat_py 에 path dispatcher 한 곳 신설**:

```python
# swat_py/forecast/paths.py
from pathlib import Path

def resolve_member_root(cfg, mode: str, year: int, season: str,
                        scenario: str | None = None) -> Path:
    if mode == "operational":
        return Path(cfg.OperationalDir) / str(year) / season
    if mode == "hindcast":
        return Path(cfg.HindcastDir)    / str(year) / season
    if mode == "scenarios":
        assert scenario is not None, "scenarios 모드는 scenario 명 필수"
        return Path(cfg.ScenariosDir)   / str(year) / season / scenario
    raise ValueError(f"unknown mode: {mode}")
```

- **scenarios/ 의 멤버 폴더 규칙은 operational/hindcast 와 동일하게** `member_NNNN/<stn>.csv` 로 통일 → swat_py 의 `_discover_members(...)` 가 단일 로직으로 모든 모드를 처리.
- **사용자 정의 시나리오는 yaml `scenarios.user[]` 로 선언** — builder type 4종(`climatology`, `historical_year`, `perturbation`, `composite`) 으로 표현.

## 7. 권장안 채택 시 후속 작업 (구현 순서)

1. **acidwg_py.scenarios** — 신규 서브패키지. `build_climatology(...)`, `build_historical_year(...)`, `build_perturbation(...)`, `build_composite(...)` 4 builder.
2. **acidwg_py.yaml** — `scenarios:` 섹션 추가 (forecast_window, climatology, worst_drought, user[]).
3. **acidwg-scenarios** — CLI 진입점 신설. `--scenario <name>` 또는 `--all` 옵션.
4. **swat_py.config.env** — `OperationalDir`, `HindcastDir`, `ScenariosDir` 속성 추가.
5. **swat_py.forecast.paths** — `resolve_member_root(...)` dispatcher 신설.
6. **swat_py.forecast.ensemble** — `mode`, `scenario_name` 인자 수용. 멤버 수 = 1 (climatology) 인 경우 분위수 산출 분기.
7. **swat_py.reservoir.level** — 댐 수지·H-V curve 모듈. 사용자 입력 초기 수위 → 시계열 수위 시뮬레이션.
8. **swat_py.dashboard.manifest** — `manifest.json` 생성기. 사용 가능한 시나리오 목록·기본 수위·임계값·캐시 위치를 메타로 기술.
9. **swat_py.dashboard.build** — `mode` 인자 추가, scenarios 분기.
10. **(선택) frontend** — JSX 슬라이더 + 시나리오 라디오. 멤버 일별 flow CSV/JSON 을 클라이언트가 직접 fetch 하여 *초기 수위만 바꾸면 즉시 재계산* 하도록 분리.

---

## 8. 결론

**안 B (Operational / Hindcast / Scenarios 3축 분리) 를 채택할 것을 권장한다.** 운영 자료에 대한 마이그레이션 비용이 없고, 시나리오의 분석 의도와 사용 제약(현재 시점 전용)이 폴더 구조 자체로 자기설명되며, Dashboard 에 노출할 때 사용자 mental model 과 자연스럽게 일치하기 때문이다. 안 A 가 가진 이론적 균일성보다 안 B 의 *명료한 의도 전달* 과 *마이그레이션 비용 0* 이 본 프로젝트의 실용적 가치에 부합한다.

채택 결정 시, 위 7절의 10단계를 순차로 진행하면 안전하게 운영 환경에 통합할 수 있다.
